[타임딜 재고 차감 시스템](/posts/redis-1-optimistic-lock-upsert-oversell-0-kotlin-110/)을 만들 때는 "Oversell 이 안 나는가"를 봤다. Redis 로 앞단을 거르고 DB Optimistic Lock 으로 정합성을 잡으면 재고는 정확히 맞았고, 거기서 검증이 끝났다고 생각했다.

그런데 얼마 뒤 [커넥션 풀은 언제 늘려야 하나](/posts/pool-sizing-resource-chain/)를 쓰면서 관점이 하나 늘었다. 스레드 · 커넥션 · DB 를 **사슬**로 보면, 어떤 요청이 실패하든 성공하든 **커넥션을 붙들고 있는 동안은 다른 요청이 못 쓴다.**

그러자 타임딜이 다시 걸렸다.

> 재고 100 에 요청 2,000 이면 1,900 건은 확정 실패다. 그 1,900 건이 "너 실패야"를 듣기까지 커넥션을 붙들면, **풀이 마르지 않을까?**

Oversell 만 볼 때는 안 보이던 질문이다. 재고는 정확히 100 개 팔렸으니 그 측정에서는 아무 문제가 없었다. 문제가 있다면 **타임딜과 아무 상관 없는 요청** 쪽에 있을 텐데, 그때 측정에는 그 요청이 아예 없었다.

그래서 다시 쟀다. 이 글은 그 기록이다.

## 1. 무엇을 재려고 했나

질문이 "Oversell 이 나는가"에서 "**무관한 요청이 밀리는가**"로 바뀌었으니, 재는 대상도 바뀌어야 했다.

이전 측정의 문제는 두 가지였다.

**첫째, 밀려나는 쪽이 측정에 없었다.** 구매 요청만 쐈으니 "타임딜이 다른 요청을 밀어낸다"를 확인할 대상 자체가 없었다.

**둘째, 부하의 크기에 근거가 없었다.** 재고 100 에 2,000 을 넣었는데 왜 2,000 인지 답할 수 없었다. 그냥 큰 숫자였다.

그래서 시나리오를 다시 정했다. 파라미터를 도메인에서 가져오는 걸 원칙으로 잡았다.

| 파라미터 | 값 | 왜 이 값인가 |
|---|---|---|
| 초과청약 배수 | 재고 100 대비 요청 6,000 | 확정 실패가 통과보다 압도적으로 많아야 앞단 거부가 값을 한다. **이 비율이 설계의 전제다** |
| 도착 형태 | `ramping-arrival-rate`, 피크 초당 1,500 을 3초 | 타임딜은 "N 명이 앉아 있는" 게 아니라 오픈 순간 요청이 쏟아지는 것이다. VU 를 쌓으면 측정기가 먼저 병목이 된다 |
| 경쟁 트래픽 | 상품 조회 초당 50 건, 전 구간 | **이게 밀려나는 쪽이다.** 이 지연이 주 지표다 |
| 관측 지점 | `hikaricp.connections.pending` | 조회가 느려진 것과 풀이 마른 것은 다른 얘기다. 원인을 보려면 풀을 직접 봐야 한다 |

그리고 **비교 대상이 필요했다.** "Redis 가 자원을 지킨다"는 Redis 를 켜고 재서는 확인되지 않는다. 없는 쪽과 나란히 놓아야 한다.

## 1-1. AI 를 어디까지 썼나

이 측정은 Claude 와 같이 돌렸다. 무엇을 맡기고 무엇을 안 맡겼는지 적어 둔다.

**내가 정한 것**

- 무엇을 재는가 — "Oversell" 이 아니라 "무관한 요청의 지연"으로 질문을 바꾼 것
- 왜 그 숫자인가 — 초과청약 배수를 기준으로 파라미터를 잡고, 근거 없는 부하를 기각한 것
- 결과가 내 가정을 지지하는가 — 원래 가정은 "DB 엔 재고 수만큼만 온다"였고, 실측과 대조해 어디까지 맞는지 판단한 것
- 다음에 무엇을 재는가 — 조회 지연만으로는 원인을 말할 수 없다고 보고 풀 스윕을 결정한 것

**AI 가 한 것**

- k6 하네스 작성 — 도착률 기반 시나리오, 구간별 p95 분리 집계, 러너 스크립트
- 반복 실행과 수치 정리 — 구성별 3회, 중앙값, 표 정리
- 방법 제안 — **"재고 키를 크게 덮으면 코드 변경 없이 대조군이 된다"는 AI 가 낸 아이디어다.** `pending` 을 200ms 간격으로 샘플링하자는 것도 마찬가지다

**내가 걸러낸 것**

제안이 다 맞지는 않았다. 초당 3,000 측정을 결과에 넣자는 흐름이 있었는데, 그 구간은 측정기와 애플리케이션이 CPU 를 나눠 쓰다 먼저 무너져서 편차가 20배였다. **숫자가 나왔다고 결론에 쓰면 안 되는 구간**이라 뺐다.

경계가 어디냐를 두고도 한 번 갈렸다. 700 rps 단발 측정에서 두 구성이 같게 나오자 "효과가 관측되지 않는다"로 정리될 뻔했는데, 그건 효과가 없는 게 아니라 **경계 아래를 찍은 것**일 수 있어서 요청률을 올려가며 다시 훑었다.

**정리하면 — 시나리오와 판단은 내가, 하네스와 반복은 AI가, 채택 여부는 다시 내가.** 아이디어가 어디서 나왔는지보다 그걸 쓸지 말지를 근거로 정했는지가 중요하다고 봤다.

## 2. 어떻게 했나 — 코드를 안 고치고 대조군 만들기

문제는 "Redis 없는 버전"을 어떻게 만드느냐였다. 코드를 분기하면 그 분기 자체가 변수가 된다.

**재고 키를 크게 덮으면 된다.** Lua 스크립트는 `현재 재고 >= 요청 수량`일 때만 차감하는데, 재고를 `99999999` 로 세팅하면 항상 통과한다. 필터가 사실상 없는 것과 같아지고, **DB Optimistic Lock 이 유일한 거부 주체**가 된다.

```bash
docker exec redis redis-cli SET "stock:$DEAL_ID" 99999999
```

코드는 한 줄도 안 고쳤다. DB 재고는 양쪽 다 100 이라 성공 건수는 같아야 하고, 실제로 모든 런에서 정확히 100 이었다.

측정 절차에서 통제한 것도 적어 둔다.

- **런 전 데이터·통계 초기화** — 딜·구매 행이 쌓이면 조회 비용이 달라져 런끼리 비교가 안 된다
- **두 구성을 번갈아 실행** — 머신 상태가 시간에 따라 변하므로, 한쪽을 몰아 돌리면 그 드리프트가 구성 차이로 오독된다
- **워밍업 런 폐기** — 직전 부하가 무거우면 첫 런이 그 여파를 받는다

## 3. 결과 — DB 도달

`pg_stat_user_tables`로 실제 스캔 수를 셌다.

| | 필터 OFF | 필터 ON |
|---|---:|---:|
| `time_deals` / 요청 | 6.13 ~ 7.58 | **0.08 ~ 0.11** |
| `time_deal_purchases` / 요청 | 0.02 | **0.02** |
| 합계 | 약 6.8회 | **0.11회** |
| 구매 p95 | 144 ~ 203 ms | **0.89 ~ 0.98 ms** |

요청 6,000건 중 DB까지 온 것은 500~680건이다. 재고 100보다 큰 이유는 재고가 마르는 동안 도착한 요청들이 0차를 통과하기 때문이다. 요청 수 기준으로는 9%.

대조군이 6.8회인 이유는 실패 요청 하나가 `findCurrentVersion` 3번 + `UPDATE` 3번을 쓰기 때문이다. 재시도 3회가 실패 경로에서 왕복을 배로 만든다.

### 3-1. 커넥션 풀이 실제로 마르는가

여기까지는 "조회가 느려졌다"는 증상이다. 그게 풀 때문인지는 별도로 봐야 한다.

풀 크기를 바꿔가며 스파이크 동안 `hikaricp.connections.pending`을 200ms 간격으로 샘플링했다. 초당 1,500 고정.

| 풀 | | 조회 p95 | active 최대 | pending 최대 |
|---:|---|---:|---:|---:|
| **10** | 필터 ON | 2.1 ms | 1 / 10 | **0** |
| | 필터 OFF | 869 ms | 10 / 10 | **930** |
| **20** | 필터 ON | 2.7 ms | 7 / 20 | **0** |
| | 필터 OFF | 323 ms | 20 / 20 | **370** |
| **40** | 필터 ON | 2.4 ms | 3 / 40 | **0** |
| | 필터 OFF | 140 ms | 40 / 40 | **267** |

**대조군은 모든 풀 크기에서 100% 포화되고 대기열이 쌓인다. 필터가 있으면 어느 크기에서도 마르지 않는다** — 최대 7개를 썼다.

여기서 "커넥션 풀을 지킨다"가 추론에서 관측으로 바뀐다.

### 3-2. 풀만 늘리면 되지 않나

이 설계에 대한 가장 자연스러운 반론이라 직접 쟀다.

풀을 10에서 40으로 4배 늘리자 869ms가 140ms로 6배 개선됐다. **완화는 된다.** 그런데 같은 조건에서 필터가 있는 쪽은 2.4ms다. 그리고 PostgreSQL은 커넥션마다 백엔드 프로세스를 띄우고, 그 비용은 인스턴스 수만큼 곱해진다.

더 중요한 건 충돌 쪽이다.

```
pool 10 → 버전 충돌 4,978
pool 20 → 5,574
pool 40 → 5,899     사실상 전량
```

**풀을 키울수록 충돌이 늘었다.** 커넥션을 더 주면 같은 row를 동시에 때리는 요청이 늘고, 충돌이 늘면 재시도가 늘고, 재시도가 늘면 왕복이 는다. 늘린 자원의 일부가 경합 증폭으로 되돌아온다.

**위 절대 수치는 노트북 한 대에서 나온 값이라 다른 환경에서 그대로 재현되지 않는다.** 규모와 무관하게 남는 결론은 하나다 — 풀 확대는 선형으로 먹히지 않는다. 경합이 증폭하기 때문이다.

### 3-3. 언제 값을 하고 언제 안 하나

조회 p95, 스파이크 중 기준이다.

| 피크 | 필터 ON | 필터 OFF |
|---:|---:|---:|
| 초당 700 | 2.0 ~ 3.0 ms | 2.7 ~ 11.0 ms |
| **초당 1,500** | **2.4 ~ 3.2 ms** | **131 ~ 191 ms** |

**초당 700 아래에서는 두 구성이 사실상 같다.** 거부될 요청이 풀을 경합시킬 만큼 많지 않다. 이 구간에서 Redis는 이득 없이 "재고의 두 번째 진실"이라는 비용만 남긴다.

**이 설계를 안 써도 되는 조건이 여기다.** 재고 대비 요청이 이 정도로 몰리지 않으면 DB 단독 + Optimistic Lock으로 충분하다. 도입 근거를 말할 수 있으려면 도입하지 않을 근거도 같이 말할 수 있어야 한다고 본다.

초당 3,000도 재봤지만 결론에서 뺐다. 양쪽 다 무너지는 데다 필터 ON의 편차가 20배였다. k6와 애플리케이션이 같은 머신에서 CPU를 나눠 쓰는 한계다. 측정기가 먼저 무너지는 구간의 숫자로는 아무 말도 하지 않기로 했다.

### 3-4. 정합성은 전 구간에서 유지됐다

```
구매 성공        100        재고와 정확히 일치
Oversell         없음
5xx                0
DB remaining       0
```

초당 3,000 · 필터 OFF로 12,000 요청을 몰아도 성공은 정확히 100건이고 5xx는 0이다. **정합성은 이 실험의 어떤 변수에도 흔들리지 않았다.** 위 논의는 전부 정합성이 아니라 자원에 관한 것이다.

## 4. 설계에서 같이 정한 것

부하를 걸어보면서 같이 확정한 두 가지다.

**판매 판정을 상태가 아니라 시간에 맡겼다.** `TimeDeal.create()`는 `SCHEDULED`로 만드는데 판매 판정이 `status == ACTIVE`를 요구하면, 전이가 돌기 전까지 아무도 못 산다. 그래서 **판단 주체를 상태가 아니라 시간으로 뒀다.**

```kotlin
fun isActiveAt(now: Instant): Boolean =
    now in startAt..endAt && status != TimeDealStatus.SOLD_OUT && status != TimeDealStatus.ENDED
```

상태 라벨은 5초 주기 워커가 뒤따라간다. 라벨을 판단 주체로 삼으면 워커 주기만큼 "시작 시각은 지났는데 못 사는" 창이 생기는데, 그 창이 하필 타임딜에서 가장 중요한 순간과 겹친다. 대가는 `status` 컬럼이 최대 5초 동안 진실이 아니라는 것이고, 얻는 건 워커가 죽어도 오픈 시각에 판매가 열린다는 것이다.

**실패를 사유별로 나눠야 셀 수 있다.** 재고 소진과 버전 충돌은 클라이언트가 해야 할 일이 정반대다. 앞은 재시도해도 의미가 없고, 뒤는 재시도하면 성공할 수 있다. 그런데 둘 다 `409 STOCK_EXHAUSTED`로 나가면 구분할 방법이 없다.

`STOCK_VERSION_CONFLICT`를 분리하고 `VersionConflict(attempts)`가 시도 횟수를 싣게 했다. HTTP 상태는 둘 다 409다 — 상태 충돌인 건 같고, 409를 종료 상태로 취급하는 클라이언트를 깨뜨리지 않는다.

**이 분리가 없으면 위 풀 스윕 표의 충돌 열을 만들 수 없다.** 관측 가능성은 대시보드가 아니라 실패를 표현하는 타입에서 시작한다.

## 5. 놓친 것

- **필터가 있을 때의 한계를 모른다.** 어느 풀 크기에서도 마르지 않아 경계를 못 찾았다. "안 무너진다"가 아니라 **"이 규모에서는 안 무너진다"**까지가 지금 말할 수 있는 전부다.
- **초당 3,000 이상을 못 잰다.** 측정기가 먼저 무너진다. k6를 다른 머신으로 분리해야 한다.
- **재시도 3회가 적절한지 모른다.** 정상 구성에서 관측된 충돌이 초당 1,500에서 2건뿐이라 표본이 부족하다.
- **경계의 정확한 위치.** 700~1,500 사이를 촘촘히 훑지 않았다.
- **Redis가 죽으면 0차·2차가 사라진다.** 정합성은 DB OL이 지키지만 자원 격리는 통째로 없어진다. 폴백은 없다.

### 5-1. 남는 것

부하 테스트를 성능 재는 도구로만 보면 이런 건 안 나온다. 이번에 얻은 건 응답 시간 숫자가 아니라 **이 설계가 언제 값을 하고 언제 안 하는지의 경계**다.

그리고 그 경계를 말할 수 있게 된 건 대조군 덕이다. 켜고 잰 숫자는 "빠르다"밖에 말해주지 않는다. 끄고 같이 재야 **무엇 때문에 빠른지**가 나온다.
