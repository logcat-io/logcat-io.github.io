4월에 [타임딜 재고 차감 시스템 글](/posts/redis-1-optimistic-lock-upsert-oversell-0-kotlin-110/)을 썼다. Redis Lua로 1차 차단하고 DB Optimistic Lock으로 정합성을 잡는 구조였고, 그 글에 이렇게 적었다.

> Redis 1차 필터 덕분에 DB는 재고량에 비례하는 소수의 요청만 처리하면 되도록 설계되었다.

넉 달 뒤에 다시 열었다. 부하 시나리오가 마음에 안 들어서였다. 재고 100에 2,000을 넣은 건 맞는데 왜 2,000인지 근거가 없었고, 무엇보다 **"타임딜이 다른 요청을 밀어낸다"가 이 설계의 전제인데 측정에 밀려나는 쪽이 없었다.** 구매 요청만 쏘고 있었다.

그래서 상품 조회를 초당 50건씩 전 구간 흘리고, 중간에 타임딜 스파이크를 얹었다. 그리고 Redis 재고 키를 크게 덮어 1차 필터만 무력화한 대조군을 만들었다. 코드는 한 줄도 안 고쳤다.

재려던 건 응답 시간이었는데, 먼저 나온 건 다른 거였다.

## 요청 전량이 DB를 두 번씩 치고 있었다

`pg_stat_user_tables`로 실제 도달 건수를 셌다. 재고 100, 구매 요청 5,999건.

```
time_deals           스캔 6,115   →  요청당 1.02회
time_deal_purchases  스캔 5,950   →  요청당 0.99회
```

재고 소진으로 거부될 5,899건도 예외 없이 DB를 두 번 읽고 나갔다. "재고량에 비례하는 소수"가 아니라 전량이었다.

## 코드만 봐도 보였을 것이다

먼저 인정할 게 있다. 이건 측정까지 안 가도 찾을 수 있었다. 문제의 함수는 40줄이고 순서가 그대로 보인다.

```kotlin
val deal = timeDealQueryPort.findById(command.timeDealId)   // DB
validator.check(deal, command.quantity, now)
val purchased = timeDealQueryPort.getPurchasedQuantity(...)  // DB
stockDecreaser.decrease(deal.id, command.quantity)           // 여기서 처음 Redis
```

Redis가 네 번째다. 이 코드를 처음 보는 사람이라면 "재고 확인이 왜 마지막이지?"가 먼저 나왔을 것이다.

나는 못 봤다. 4개월 동안. 이유는 짐작이 가는데, 내가 `StockDecreaser` 안에 이렇게 적어뒀기 때문이다.

```kotlin
// 실패 시 DB 에 접근하지 않음 -> DB 부하 차단히 핵심 목적
// Redis 를 통과했으므로 "유력 후보" 만 DB 에 도달한다.
```

이 주석은 거짓이 아니다. `decrease()` **안에서는** 정말로 Redis 실패 시 DB를 안 친다. 틀린 건 그 함수를 부르기 전에 이미 두 번 조회하던 호출자였다.

**파일 하나만 읽으면 맞고, 흐름 전체를 보면 틀린 상태였다.** 그리고 그 파일에 의도가 적혀 있으니 나는 그걸 읽고 확인했다고 생각했다.

주석의 사정거리는 그 파일까지다. 흐름이 맞는지는 흐름을 봐야 안다.

## 그래도 측정이 필요했던 이유

그럼 측정은 의미가 없었나. 그건 아니라고 본다.

주석이 없었으면 `1.02회`라는 숫자를 보고도 "원래 이런 건가" 하고 넘어갔을 것이다. **어긋남은 기준이 있어야 보인다.** 의도를 적어두지 않았다면 이건 어긋남이 아니라 그냥 현재 상태였다.

그리고 코드를 다시 읽게 만든 게 측정이었다. 4개월 동안 안 읽었는데, 숫자가 이상해서 읽었다.

## 두 가지를 고쳤다

**Redis 재고 확인을 맨 앞으로 옮겼다.** 차감이 아니라 `GET`이라 실패해도 되돌릴 게 없다. 롤백 경로가 늘지 않는다. 원자적 판정은 여전히 뒤쪽 Lua가 한다 — 앞의 확인을 통과했다가 Lua에서 실패하는 요청이 생기는데, 그건 결함이 아니라 필터의 성격이다. 이 자리는 게이트가 아니라 **명백히 안 될 요청을 싸게 걷어내는 곳**이다.

**`getPurchasedQuantity` 선검사를 지웠다.** 원글 4-4절에서 UPSERT WHERE로 1인 한도를 원자적으로 닫아뒀는데, 그 앞에 굳이 SELECT로 한 번 더 확인하고 있었다.

```kotlin
.onConflict(TIME_DEAL_ID, USER_ID).doUpdate()
    .where(QUANTITY.plus(quantity).le(maxPerUser))   // 이미 원자적
```

정확성에 필요 없는 코드였다. 재구매자 한 명의 Redis 롤백을 아끼려고 **모든 요청**이 DB를 한 번 더 치는 거래였던 셈이다. 같은 사용자가 동시에 20회 시도해도 1건만 성공하는 것을 통합 테스트로 확인했다.

| | 필터 OFF | 순서 이전 | 순서 수정 |
|---|---:|---:|---:|
| DB 왕복 / 요청 | 약 6.8회 | 2.01회 | **0.11회** |
| 구매 p95 | 144~203 ms | 10.62 ms | **0.89~0.98 ms** |

## 그래서 무엇이 지켜졌나

여기까지는 "조회가 느려졌다"는 증상만 본 것이다. 그게 커넥션 풀 때문인지는 확인하지 않았다.

HikariCP 풀 크기를 바꿔가며 스파이크 동안 `hikaricp.connections.pending`을 200ms 간격으로 샘플링했다. 초당 1,500건 고정.

| 풀 | | 조회 p95 | active 최대 | pending 최대 |
|---:|---|---:|---:|---:|
| **10** | 필터 ON | 2.1 ms | 1 / 10 | **0** |
| | 필터 OFF | 869 ms | 10 / 10 | **930** |
| **20** | 필터 ON | 2.7 ms | 7 / 20 | **0** |
| | 필터 OFF | 323 ms | 20 / 20 | **370** |
| **40** | 필터 ON | 2.4 ms | 3 / 40 | **0** |
| | 필터 OFF | 140 ms | 40 / 40 | **267** |

대조군은 모든 풀 크기에서 100% 포화되고 대기열이 쌓인다. 필터가 있으면 어느 크기에서도 마르지 않는다 — 최대 7개를 썼다.

**여기서 "커넥션 풀을 지킨다"가 추론에서 관측으로 바뀌었다.**

## 풀만 늘리면 되지 않나

이 설계에 대한 가장 자연스러운 반론이라 직접 재봤다.

풀을 10에서 40으로 4배 늘리자 869ms가 140ms로 6배 개선됐다. **완화는 된다.** 그런데 같은 조건에서 필터가 있는 쪽은 2.4ms다.

더 흥미로운 건 충돌 쪽이다.

```
pool 10 → 버전 충돌 4,978
pool 20 → 5,574
pool 40 → 5,899     사실상 전량
```

**풀을 키울수록 충돌이 늘었다.** 커넥션을 더 주면 같은 row를 동시에 때리는 요청이 늘고, 충돌이 늘면 재시도가 늘고, 재시도가 늘면 왕복이 는다. 늘린 자원의 일부가 경합 증폭으로 되돌아온다.

이게 이 측정에서 유일하게 규모와 무관한 결론이다. 위 숫자들은 노트북 한 대에서 나온 값이라 다른 환경에서 그대로 재현되지 않는다. 하지만 **"풀 확대는 선형으로 먹히지 않는다, 경합이 증폭하기 때문이다"**는 어디서든 참이다.

## 언제 값을 하고 언제 안 하나

조회 p95, 스파이크 중 기준이다.

| 피크 | 필터 ON | 필터 OFF |
|---:|---:|---:|
| 초당 700 | 2.0 ~ 3.0 ms | 2.7 ~ 11.0 ms |
| **초당 1,500** | **2.4 ~ 3.2 ms** | **131 ~ 191 ms** |

**초당 700 아래에서는 두 구성이 사실상 같다.** 거부될 요청이 풀을 경합시킬 만큼 많지 않다. 이 구간에서 Redis는 이득 없이 "재고의 두 번째 진실"이라는 비용만 남긴다.

이 설계를 **안 써도 되는 조건**이 여기다. 재고 대비 요청이 이 정도로 몰리지 않으면 DB 단독 + Optimistic Lock으로 충분하다.

초당 3,000도 재봤지만 결론에서 뺐다. 양쪽 다 무너지는 데다 필터 ON의 편차가 20배였다. k6와 애플리케이션이 같은 머신에서 CPU를 나눠 쓰는 한계다. 측정기가 먼저 무너지는 구간의 숫자로는 아무 말도 하지 않기로 했다.

## 재는 김에 걸린 두 가지

부하를 재려다 엉뚱한 걸 발견했다.

**API로 만든 딜은 한 개도 팔 수 없었다.** `TimeDeal.create()`는 항상 `SCHEDULED`로 만드는데 `ACTIVE`로 바꾸는 코드가 어디에도 없었다. `isActiveAt()`은 `status == ACTIVE`를 요구한다. 첫 측정에서 구매 2,099건이 통째로 400으로 떨어진 원인이 이거였고, 이전 측정들은 SQL로 상태를 직접 올려서 돌린 것이었다.

**단위 테스트 27건이 통과하는 상태였다.** 테스트는 내가 물어본 것만 답한다.

고칠 때 판단 주체를 상태가 아니라 시간으로 옮겼다. 전이 워커만 추가하면 워커 주기만큼 "시작 시각은 지났는데 못 사는" 창이 생기는데, 그 창이 하필 타임딜에서 가장 중요한 순간과 겹친다. 상태 라벨은 5초 주기 워커가 뒤따라가고, 판매 가능 여부는 `startAt..endAt`이 정한다. 대가는 `status` 컬럼이 최대 5초 동안 진실이 아니라는 것이다.

**버전 충돌이 "품절"로 나가고 있었다.**

```kotlin
StockDecreaser.Result.VersionConflict -> throw StockExhaustedException()
```

재고가 남아 있는데 `409 STOCK_EXHAUSTED`를 응답했다. 그 예외에 "클라이언트는 409를 보면 재시도해도 의미 없음을 알 수 있다"고 주석까지 달아놨는데, 버전 충돌은 재시도하면 성공할 수 있는 실패다. 정반대 신호를 주고 있었다.

`STOCK_VERSION_CONFLICT`로 분리하고 시도 횟수를 실어 보내게 고쳤다. 이걸 고치기 전에는 위 표의 충돌 숫자를 만들 수 없었다. 충돌 횟수를 알려면 Redis `INCRBY` 호출 수를 세는 우회로가 필요했다.

**관측 가능성은 대시보드가 아니라 실패를 표현하는 타입에서 시작한다.**

## 원글 10-4절을 다시 읽었다

4월 글 마지막에 이렇게 써뒀다.

> 부하 테스트를 "성능을 재는 도구"라기보다 "설계의 모서리를 드러내는 도구"에 가깝게 보게 됐다.

넉 달 뒤에 그 도구가 그 글의 주장 하나를 깼다. 성능을 재려던 게 아니라 시나리오가 마음에 안 들어서 다시 짰을 뿐인데, 그 과정에서 의도와 구현이 어긋난 지점, 딜이 절대 안 팔리는 버그, 실패 코드가 정반대 신호를 주던 것까지 같이 나왔다.

그래서 하나 더 붙이자면 — **만든 것이 의도대로 동작하는지는, 의도를 적어두고 나중에 직접 재봐야 안다.** 코드는 컴파일되고 테스트는 통과하고 정합성도 맞았지만, 정작 이 설계의 존재 이유였던 "DB 도달 차단"은 처음부터 지켜지지 않고 있었다.

아직 못 밝힌 것도 남겨둔다. 필터가 있을 때는 어느 풀 크기에서도 마르지 않아서 **한계를 못 찾았다.** "안 무너진다"가 아니라 "이 규모에서는 안 무너진다"까지가 지금 말할 수 있는 전부다.
