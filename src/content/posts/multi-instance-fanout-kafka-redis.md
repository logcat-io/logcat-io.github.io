[1편](/posts/sse-registry-concurrency/) 마지막에 이렇게 썼다.

> 인스턴스를 두 벌 띄우면 각자 자기 메모리에 자기 맵을 들고 있다. 사용자가 A에 붙어 있는데 이벤트가 B에서 발행되면 못 받는다. (…) 일단 두 벌 띄워 보려고 한다. 깨지는 걸 보고 나서 정한다.

이번 편은 그 다음이다. **인스턴스를 늘려도 이벤트가 사용자에게 닿게 만드는 데 무엇이 필요했는지**를 순서대로 적는다. Outbox를 들이고, Kafka를 들이고, 마지막 한 칸을 Redis로 채웠다.

각 단계마다 "왜 이걸 골랐나"가 핵심이다. 도구를 먼저 정해 놓고 쓸 데를 찾은 게 아니라, 앞 단계에서 남은 구멍이 다음 도구를 불러왔다.

## 출발점 — 연결이 프로세스 메모리에 산다

1편의 레지스트리는 이렇게 생겼다.

```kotlin
private val emitters = ConcurrentHashMap<UUID, MutableSet<SseEmitter>>()
```

프로세스 안의 맵이다. 인스턴스를 두 벌 띄우면 맵도 두 개다. 사용자가 A에 붙어 있는데 이벤트가 B에서 발행되면, B의 맵에는 그 배송의 emitter가 없다. **조용히 지나간다.**

`compute`를 아무리 잘 써도 해결되는 문제가 아니다. 원자성 문제가 아니라 위치 문제다.

여기까지는 코드만 읽어도 나온다. 그래도 두 벌 띄우고 8080 한쪽에만 SSE를 붙여 확인했다. 상태를 바꿔도 화면은 그대로였다. 예상한 대로다.

**읽어서 아는 것과 봐서 아는 것은 남는 게 다르다.** 실제로 이 관측이 나중에 기준선 역할을 한다.

## 첫 번째 선택 — 이벤트를 프로세스 밖으로 (Kafka)

문제를 한 줄로 줄이면 **"이벤트가 그걸 만든 프로세스 안에서만 존재한다"** 다.

그러면 방향은 하나다. 이벤트를 프로세스 밖에 두면 된다. 어느 인스턴스가 상태를 바꿨든, 이벤트는 모든 인스턴스가 볼 수 있는 곳에 있어야 한다.

Kafka를 고른 이유는 세 가지였다.

| 필요한 것 | Kafka가 주는 것 |
|---|---|
| 발행자와 소비자를 분리 | 브로커가 중간에 선다 — 서로를 모른다 |
| 이벤트가 사라지지 않을 것 | 디스크에 남는 로그. 소비했다고 지워지지 않는다 |
| 같은 배송의 순서 보장 | 파티션 키를 `deliveryId`로 두면 한 배송은 한 파티션 |

세 번째가 특히 컸다. 배송 상태는 `ORDER_RECEIVED → PREPARING → PICKED_UP` 처럼 **순서가 의미인 데이터**다. `PICKED_UP` 다음에 `PREPARING`이 도착하면 화면이 뒤로 간다. 파티션 키를 배송 ID로 잡으면 같은 배송의 이벤트는 항상 같은 파티션에 들어가고, 파티션 안에서는 순서가 지켜진다.

이 작업을 하는 동안 컨슈머는 받은 메시지를 로그로만 찍었다. 화면으로 가는 길이 잠깐 비는데, **먼저 옮기고 나서 다시 잇는 게 맞는 순서다.** 옮기는 중에 화면까지 붙여 두면 무엇 때문에 도달했는지 갈라내기 어려워진다.

## 두 번째 선택 — 유령 이벤트를 막으려고 (Outbox)

Kafka를 붙이고 나서 일부러 잘못 만든 구간이 하나 있다. 상태 변경 트랜잭션 **안에서** 곧바로 Kafka로 발행하는 코드였다.

```kotlin
@Transactional
fun execute(...) {
    delivery.changeStatus(next)
    repository.save(delivery)
    kafkaTemplate.send(TOPIC, event)   // ← 트랜잭션 안
}
```

이 뒤에 예외가 나면 어떻게 되나. **DB는 롤백되고 Kafka 메시지는 그대로 남는다.** 브로커에는 트랜잭션 취소라는 개념이 없다. 이미 나간 건 나간 거다.

그래서 DB에는 없는 상태 변경이 사용자 화면에는 뜬다. 새로고침하면 사라진다. 로그에 에러는 남지만 그 에러와 화면의 유령을 연결 짓기까지가 멀다. **조용한 쪽이 시끄러운 쪽보다 늘 위험하다고 생각한다.**

Outbox는 이걸 구조로 막는다.

```
[트랜잭션 안]
  deliveries UPDATE
  outbox_events INSERT      ← 발행할 "의도"만 적는다
  커밋

[트랜잭션 밖 · 별도 워커]
  PENDING 행을 집어서 Kafka로 보낸다
  성공하면 PUBLISHED 로 마킹
```

트랜잭션 안에서는 **"이 이벤트를 보내겠다"는 기록만 남긴다.** 실제로 브로커에 밀어 넣는 일은 커밋이 끝난 뒤 별도 워커가 한다.

롤백되면 `outbox_events` INSERT도 같이 사라진다. **보낼 이벤트 자체가 존재하지 않으니 유령이 나올 자리가 없다.** 이건 "조심해서 짜자"가 아니라 원자성이 DB로 내려간 것이다.

워커는 `FOR UPDATE SKIP LOCKED`로 행을 집는다. 워커가 여러 대여도 같은 행을 두 번 집지 않고, 잠긴 행은 기다리지 않고 건너뛴다.

대신 얻는 게 있으면 내주는 것도 있다.

- **지연이 붙는다.** 커밋 즉시가 아니라 다음 주기에 나간다
- **중복 발행이 가능하다.** 발행 성공 후 마킹 전에 죽으면 다음 워커가 다시 보낸다

두 번째는 감수하기로 했다. Outbox가 주는 건 **최소 한 번**이지 정확히 한 번이 아니다. 중복은 소비 쪽에서 멱등으로 받는 게 맞다고 본다. 다만 여기서는 "같은 상태를 두 번 그린다"가 화면상 무해해서 우선순위를 뒤로 뒀다.

여기까지 하고 컨슈머가 다시 레지스트리로 밀게 한 뒤, 인스턴스 한 대에서 프레임이 도달하는 걸 확인했다. **여기가 기준선이다.** 이게 있어야 다음 단계에서 무엇이 달라졌는지 말할 수 있다.

## Kafka가 하는 일과 하지 않는 일

이벤트는 이제 프로세스 밖에 있다. 그러면 인스턴스를 늘려도 될까.

Kafka 문서를 다시 읽다가 걸린 문장이 있었다.

> 하나의 파티션은 그룹 안에서 **정확히 하나의 컨슈머**에게만 배정된다.

내가 필요한 건 "모든 인스턴스가 모든 이벤트를 받는 것"인데, 인스턴스들이 같은 그룹에 있으면 이벤트는 **나눠진다.** 브로드캐스트가 아니라 분배다.

```
[같은 group id]                [필요한 것]
  partition 0 → 인스턴스 A        모든 메시지 → A "그리고" B
  partition 1 → 인스턴스 A
  partition 2 → 인스턴스 B
  한 메시지는 A "또는" B
```

이건 Kafka의 결함이 아니라 설계 목적 그 자체다. 컨슈머 그룹은 **처리량을 나눠 갖기 위한** 장치다. 같은 메시지를 두 컨슈머가 중복 처리하지 않는 게 핵심 가치고, 팬아웃은 정확히 그 반대를 요구한다.

그래서 다시 두 벌 띄웠다. 8080에 붙은 SSE로는 프레임이 오지 않았다. 예상한 그림이다.

## "예상대로다"와 "증명됐다"는 다르다

여기서 바로 Redis를 깔 수도 있었다. 예상했고 예상대로 됐으니까.

그런데 지금 손에 있는 관측은 **"8080에 안 왔다"** 하나뿐이다. 이걸로 "파티션 배정 때문이다"까지 가려면 한 칸이 빈다. 파티션이 3개고 인스턴스가 2대면 배정이 2:1로 갈리는데, 8080이 하나만 맡았다면 도달 확률이 1/3이다. **4회 연속 미도달은 확률 20%로 그냥 나온다.** 회차를 늘려도 "이번엔 운이 나빴다"를 완전히 지우지는 못한다.

그래서 확률을 빼고 배정 자체를 통제하려고 **8081을 죽였다.**

리밸런싱으로 8080이 파티션 3개를 전부 가져간다. 코드는 그대로다. 바뀐 건 배정 하나뿐이다.

```
8081 가동 · 8081이 소비   →  미도달
8081 종료 · 8080이 소비   →  도달
```

같은 코드, 같은 절차, 배정만 뒤집었더니 결과가 뒤집힌다.

**예측할 수 없는 건 어느 인스턴스가 그 파티션을 맡느냐이지, 배정이 정해진 뒤의 인과가 아니다.** 소비한 인스턴스가 결과를 결정한다.

이 한 단계가 없으면 나중에 비슷한 증상을 만났을 때 또 처음부터 의심하게 된다. **"그럴 것 같다"로 넘어간 자리는 반드시 다시 돌아온다.**

## group id를 인스턴스마다 다르게 주면?

제일 먼저 떠오르는 대안이고, **동작은 한다.** 그룹이 다르면 각자 다 받는다. 그런데 group id를 무엇으로 만들지가 함정이었다.

```
① 인스턴스 고유값 (UUID·호스트명)
   재기동할 때마다 새 그룹이 생긴다
   → 브로커에 죽은 그룹이 쌓인다
   → 새 그룹은 auto.offset.reset=earliest 를 따라 처음부터 읽는다
   → 재기동할 때마다 과거 이벤트가 통째로 SSE로 재전송된다

② 고정 번호 (app-0, app-1)
   인스턴스에 번호를 붙여야 한다
   → 오토스케일링·컨테이너 환경과 어긋난다
   → 배송 알림 팬아웃 하나 때문에 배포 형상을 바꾸는 건 비싸다
```

그리고 둘 다 **Kafka에 인스턴스 수만큼 부하를 얹는다.** 파티션 3개 × 인스턴스 N대 = 컨슈머 3N개가 브로커에 붙는다.

스티키 라우팅(로드밸런서가 `deliveryId`로 인스턴스 고정)도 봤는데, LB에 도메인 지식을 심는 게 걸렸다. 인스턴스가 늘거나 줄면 해시가 재배치돼서 **배포할 때마다 기존 연결이 어긋난다.**

연결 위치를 DB나 Redis에 기록하는 방법도 생각했다. "이 배송은 인스턴스 A에 있다"를 적어 두고 그쪽으로만 보내는 것. 그런데 **연결은 휘발성인데 기록은 영속이다.** 프로세스가 `kill -9` 당하면 정리 안 된 행이 남고, 그 뒤로 그 배송의 이벤트는 존재하지 않는 인스턴스로 향한다. TTL과 하트비트로 막으려면 사실상 서비스 디스커버리를 직접 만드는 일이 된다.

## 세 번째 선택 — 팬아웃은 Redis가 맡는다

Kafka에서 받은 인스턴스가 Redis 채널로 다시 쏘고, **모든 인스턴스가 그 채널을 구독한다.** 연결이 어디 있든 도달한다.

```
Kafka ──→ 인스턴스 A (컨슈머)
              │
              └─→ Redis 채널 ──┬─→ 인스턴스 A 구독자 → 로컬 연결 확인 → 전송
                               └─→ 인스턴스 B 구독자 → 로컬 연결 확인 → 전송
```

Redis Pub/Sub은 저장하지 않는다. 구독 중인 모두에게 뿌리고 끝이다. 보통은 이게 약점으로 꼽히는데, **여기서는 그게 정확히 필요한 성질이다.** SSE 연결도 지금 붙어 있는 것만 의미가 있으니 둘의 수명이 맞는다.

Kafka 쪽은 손대지 않았다. 그룹 1개, 컨슈머 3개 그대로다. 늘어나는 건 Redis 구독자뿐이고 인스턴스 수만큼이다. **팬아웃은 팬아웃을 할 줄 아는 도구에 맡겼다** — 이 선택은 그게 전부다.

## 각 층이 무엇을 보장하나

세 층이 자리를 잡고 나니 역할이 깔끔하게 갈렸다.

| 층 | 보장하는 것 | 보장하지 않는 것 |
|---|---|---|
| **Outbox** | 커밋된 것은 최소 한 번 발행된다 | 중복이 없다는 것 |
| **Kafka** | 그룹 안의 누군가는 반드시 가져간다 | **누가** 가져갈지, 모두가 가져갈지 |
| **Redis Pub/Sub** | 지금 붙어 있는 모두에게 간다 | 그때 없던 구독자에게도 간다는 것 |

하나로 둘을 하려다 group id 분리 같은 무리가 나온다. 각 층에 하나씩 맡기니 오히려 층마다 단순해졌다.

## ack를 어디서 할 것인가

컨슈머를 수동 ack로 바꾸면서 순서를 정해야 했다.

```kotlin
redisPublisher.publish(event)
ack.acknowledge()
```

**재발행 뒤에 ack한다.** 반대로 하면 Redis 발행이 실패했을 때 Kafka는 이미 소비 완료로 처리돼 그 이벤트를 다시 볼 방법이 사라진다.

다만 이 ack가 보장하는 건 딱 하나다. **Kafka 소비가 끝났다는 것이지 사용자에게 도달했다는 뜻이 아니다.** Redis Pub/Sub은 fire-and-forget이라 채널에 던진 뒤의 일은 아무도 책임지지 않는다.

## 구독자가 죽으면 안 된다

`onMessage`에서 예외를 밖으로 던지면 리스너가 죽는다. 그러면 **그 인스턴스는 이후 모든 메시지를 놓친다.** 한 번의 역직렬화 실패가 그 프로세스의 팬아웃을 통째로 끄는 셈이다.

그래서 구독자 안에서 잡고 로그만 남긴다. 테스트도 그걸 겨눈다 — 깨진 payload를 채널에 직접 던진 다음, **그 뒤에 보낸 정상 메시지가 도달하는지**를 본다.

연결이 없는 배송으로 발행되는 경우도 같은 이유로 잡아 뒀다. 채널은 모두에게 뿌리니까 **이벤트를 받은 인스턴스 중 연결이 없는 쪽이 오히려 다수다.** 거기서 NPE가 나면 전부 터진다.

## 여기까지의 파이프라인, 그리고 뚫린 곳

![상태 변경 트랜잭션에서 Outbox·Kafka·Redis Pub/Sub을 거쳐 모든 인스턴스의 SSE 연결에 도달하는 파이프라인](/images/posts/multi-instance-fanout-kafka-redis/pipeline.svg)

앞쪽 절반은 Outbox가 보장한다. 커밋된 것은 반드시 브로커까지 간다.

**뒤쪽 절반은 아무것도 보장하지 않는다.** Redis Pub/Sub은 fire-and-forget이고, SSE는 그냥 열려 있는 TCP 연결이다. 구독자가 없는 순간의 메시지는 그대로 흘러간다.

그래서 정확한 문장은 이렇게 된다.

> ~~이벤트가 사용자에게 도달한다~~
> **연결이 유지되는 동안은 이벤트가 사용자에게 도달한다**

지하철에 들어가서 끊기면 그 사이 이벤트는 사라진다. 게다가 1편에서 확인한 것처럼 **닫힌 소켓에 대한 첫 write는 성공한다.** 서버는 끊긴 줄도 모르고 한 번 더 보내 봐야 안다.

## 다음

끊긴 사이를 어떻게 메울지가 남았다. 이벤트를 다 저장해 두고 재생하는 방법도 있고, 재연결 시점에 현재 상태 하나만 보내는 방법도 있다. 앞은 Kafka나 Redis Streams를 끌어와야 하고, 뒤는 DB 조회 한 번이면 된다.

배송 상태처럼 **"지금 어디까지 왔나"만 알면 되는 데이터**라면 중간 과정을 전부 재생할 이유가 없어 보인다. 다만 그건 도메인 성질에 기댄 판단이라, 정말 그런지부터 확인하고 정하려 한다.
