스키마를 짜다 보면 상태 컬럼 앞에서 한 번 멈춘다. `status` 를 PostgreSQL ENUM 타입으로 박을지, 그냥 문자열로 둘지. "ENUM이 깔끔하고 빠르다"는 말과 "실무는 문자열 쓴다"는 말이 둘 다 돌아다녀서 헷갈린다.

이 글은 그 선택의 기준을 정리해두는 글이다. 결론부터 말하면 선택을 가르는 건 성능이 아니라 **그 값 집합이 앞으로 어떻게 변할까**다. 그리고 흔히 도는 "ENUM은 락 때문에 위험하다" 같은 얘기 중엔 틀린 것도 섞여 있어서, 그것부터 걷어낸다.

## ENUM은 디스크에서 4바이트다

enum 값은 화면엔 `'PENDING'` 으로 보이지만, 디스크엔 그 라벨의 내부 식별자(oid, 4바이트)가 저장된다. 카탈로그 `pg_enum` 이 oid ↔ 라벨 대응을 들고 있다.

```sql
CREATE TYPE order_status AS ENUM ('PENDING', 'PAID', 'CANCELLED');
```

- **저장**: 4바이트 고정. `'PENDING'` 을 text로 넣으면 varlena 헤더까지 8바이트쯤 되니, enum이 오히려 작다.
- **비교**: 동등 비교는 oid 정수 비교라 빠르다.

그래서 "ENUM이라 SELECT가 느리다"는 대체로 과장이다. 런타임 성능만 보면 enum은 불리하지 않다.

문제는 성능이 아니라 값 집합을 바꿀 때다. 그런데 이 지점에 오해가 많이 꼈다.

## 오해부터: ENUM은 추가·이름 변경이 생각보다 싸다

흔히 도는 두 얘기가 실제 PostgreSQL 동작과 안 맞는다.

**"값 추가하면 락 걸려서 장애 난다" — 과장이다.**

```sql
ALTER TYPE order_status ADD VALUE 'REFUNDED';
```

이건 `pg_enum` 에 행 하나 넣는 카탈로그 작업이다. 그 타입을 쓰는 테이블을 재작성하지도, 그 테이블에 배타 락을 걸지도 않는다. 사실상 온라인이다. 공식 문서가 이 명령에 붙이는 유일한 단서는 "트랜잭션 블록 안에서 실행하면 커밋 전까지는 그 값을 못 쓴다"는 것뿐이다(PG 12 이전엔 트랜잭션 안에서 아예 못 돌렸지만 지금은 풀렸다).

배타 락과 재작성이 진짜 무서운 건 `ALTER TABLE ... ALTER COLUMN TYPE` 처럼 **컬럼 타입을 통째로 바꾸는** 작업이다. 그건 enum이든 아니든 위험하고, "값 하나 추가"와는 다른 얘기다.

**"이름 바꾸면 저장된 row도 다 UPDATE해야 한다" — 오히려 반대다.**

```sql
ALTER TYPE order_status RENAME VALUE 'WAIT_FOR_PAYMENT' TO 'PENDING_PAYMENT';
```

한 줄이면 끝난다. row는 문자열이 아니라 oid를 저장하니, 라벨만 바꾸면 기존 수백만 건이 데이터 변경 없이 자동으로 새 이름으로 보인다. 마이그레이션이 없다.

오히려 문자열로 저장했다면 `UPDATE orders SET status='PENDING_PAYMENT' WHERE status='WAIT_FOR_PAYMENT'` 로 전체 행을 쓸어야 한다. 큰 테이블이면 이쪽이 더 무겁다. 이름 변경만 놓고 보면 enum이 더 편하다.

그러니 "추가하거나 이름 바꿀 때 위험해서 enum을 피한다"는 근거는 약하다. enum이 진짜 약한 곳은 따로 있다.

## ENUM이 실제로 약한 곳

**값을 못 지운다.** PostgreSQL엔 `DROP VALUE` 가 없다. 잘못 넣은 값, 안 쓰는 값을 표준적으로 제거하는 방법이 없다. 지우려면 타입을 새로 만들고 컬럼을 갈아끼우는 큰 작업이 된다. 추가는 쉬운데 회수가 안 되는 이 비대칭이 enum의 진짜 함정이다.

**값에 정보를 못 붙인다.** 이게 실무에서 제일 크다. 상태 하나엔 보통 라벨만 있는 게 아니다. 화면 표시명, 정렬 순서, 활성/비활성 플래그, 다국어, 유효기간 같은 게 딸려 온다. enum은 '이름' 하나가 전부라 이런 걸 담을 자리가 없다. 결국 이 메타데이터를 코드나 다른 테이블로 빼게 되고, 그러면 enum을 쓴 이점이 옅어진다.

**DB 밖으로 나갈 때.** 메시지 큐, 외부 API, 다른 서비스와 상태 값을 주고받는 구조라면 계약은 어차피 문자열이다. DB 벤더에 묶인 타입에 원본을 두면 이 경계에서 매번 매핑을 신경 써야 한다.

## 기본값으로 두는 패턴: TEXT + 애플리케이션 enum

정리하면서 기본값으로 삼으려는 건 이거다.

- DB 컬럼은 `TEXT`(또는 적당한 `VARCHAR`)
- 애플리케이션(Kotlin/Java)에서 `enum` 으로 상태를 정의하고, 읽을 때 문자열 → enum, 쓸 때 enum → 문자열로 매핑
- 필요하면 enum 상수 이름과 DB 저장 문자열을 분리한다 (상수는 `PENDING_PAYMENT`, 저장 값은 따로)

얻는 것: 새 상태는 코드 enum에 상수 추가 후 배포로 끝난다. DB DDL이 없다. 값이 자주 느는 도메인(주문 상태, 프로모션 타입)에서 편하다. 타입 안전성은 애플리케이션 enum이 지키고, 이상한 문자열은 변환 단계에서 예외로 터져 빨리 잡힌다.

포기하는 것도 정직하게 적자. DB가 값을 강제하지 않으니 raw SQL이나 버그로 쓰레기 문자열이 들어갈 틈이 생긴다. 막으려면 `CHECK` 제약이나 코드 테이블 + FK를 얹는데, `CHECK` 은 값 추가 때 결국 DDL이 필요하고 FK는 조인·관리 비용이 든다. "가능한 값 목록"이 타입에 안 박혀 있어 코드를 봐야 하는 불편도 있다. 공짜가 아니다.

## 값에 정보가 붙는다면: SMALLINT + 코드 테이블

문자열에서 한 걸음 더 가는 선택지가 코드 테이블이다.

```sql
status_code smallint references order_status(code)
-- order_status(code, name, sort_order, is_active, ...) 를 데이터로 관리
```

저장은 2바이트로 더 작고, FK로 값이 강제되고, 무엇보다 표시명·정렬·활성 플래그 같은 메타데이터를 컬럼으로 붙일 수 있다. 대신 조회마다 조인(또는 캐싱)이 필요하고 테이블을 하나 더 관리한다.

세 방식을 값 관리 축으로 놓고 보면 이렇게 갈린다.

| | ENUM | TEXT + 앱 enum | SMALLINT + 코드 테이블 |
|---|---|---|---|
| 값 추가 | DDL(하지만 온라인) | 코드 배포만 | 행 INSERT |
| 값 삭제 | 사실상 불가 | UPDATE로 정리 | 행 처리(FK 주의) |
| 값에 메타데이터 | 불가 | 코드로 | **테이블 컬럼으로** |
| DB가 값 강제 | 강함 | 없음(CHECK 별도) | FK로 |
| 저장/조회 | 4B, 조인 없음 | 문자열, 조인 없음 | 2B, 조인 필요 |

## 그럼 ENUM은 언제 쓰나

버릴 필요는 없다. 값 집합이 작고 사실상 안 변하고 부가 정보도 필요 없는 필드라면 enum이 제일 깔끔하다.

- 성별, 고정된 시스템 플래그, ISO 같은 표준 코드
- 애플리케이션뿐 아니라 DB 레벨에서까지 값을 타입으로 강제하고 싶을 때

이런 필드는 삭제·추가 요구가 거의 없어서 enum의 약점(삭제 불가, 메타데이터 없음)이 안 아프고, 4바이트 고정·자기 문서화 같은 장점만 남는다. 판단은 질문 하나면 된다 — **"이 값들, 나중에 지우거나 값마다 정보를 붙일 일이 생길까?"** 아니오가 확실하면 enum, 애매하면 문자열이나 코드 테이블.

## 성능은 대개 여기서 안 갈린다

enum이냐 text냐로 SELECT가 두 배 느려지는 일은 거의 없다. PostgreSQL 성능이 갈리는 곳은 인덱스 설계, 쿼리(조인·정렬·페이징), 캐시 히트율, MVCC·vacuum·bloat, 락 경합이다. enum과 text의 차이는 그 앞에서 소수점이다.

이 선택이 실제로 남기는 비용은 런타임 성능이 아니라 값 집합을 바꿀 때의 유연성 쪽이다 — 지울 수 있나, 정보를 붙일 수 있나, DB 밖과 어떻게 주고받나.

## 정리

- enum의 런타임 성능도, 값 추가도, 이름 변경도 생각보다 멀쩡하다. 이름 변경은 오히려 문자열보다 enum이 쉽다.
- enum의 진짜 약점은 **값 삭제 불가**와 **값에 메타데이터를 못 붙이는 것**이다.
- 기본값은 TEXT + 애플리케이션 enum. 값에 정보가 붙으면 SMALLINT + 코드 테이블. 정말 안 변하는 작은 집합이면 enum도 좋은 선택이다.
