토큰 버킷이라는 이름은 여기저기서 들어봤다. 그런데 그때 이해하고 있던 건 딱 한 줄이었다.

> 고정 윈도우는 버스트가 있고, 토큰 버킷은 그게 없다.

틀린 말은 아니지만 아는 게 여기까지였다. 버스트가 실제로 얼마나 나는지, 왜 생기는지, 토큰 버킷은 그걸 어떤 방식으로 없앤 건지는 설명하지 못했다. 누가 물어보면 저 한 줄까지는 대답할 수 있고, 한 번 더 파고들면 막히는 상태였다.

그래서 말로만 듣던 걸 직접 만들어보기로 했다. 두 방식을 각각 구현해서 같은 요청을 넣어보면 저 문장이 어디까지 맞는 말인지 확인할 수 있을 것 같았다.

## 1. 비교가 성립하려면

구현에 들어가기 전에 걸리는 부분이 하나 있었다. 두 방식을 그냥 나란히 놓고 돌리면 설정값이 달라서 결과 차이가 어디서 온 건지 알 수가 없다. 한쪽이 더 많이 통과시켰다고 해도 그게 알고리즘 차이인지 그냥 한도를 헐겁게 준 건지 구분되지 않는다.

그래서 두 방식의 평균 허용률을 똑같이 맞췄다.

| | 설정 | 평균 허용률 |
|---|---|---|
| Fixed Window | limit 5 / window 10초 | 0.5 req/s |
| Token Bucket | capacity 5 / refill 0.5 tokens/s | 0.5 req/s |

10초에 5개나 초당 0.5개나 길게 보면 같은 양이다. 총량이 같으니 결과가 다르게 나온다면 그건 허용량을 나눠주는 방식의 차이라고 볼 수 있다.

시간을 다루는 부분도 손을 봤다. `System.currentTimeMillis()` 를 그대로 쓰면 실험할 때마다 `Thread.sleep` 을 호출해야 한다. 그런데 `sleep` 은 그 시간만큼 잔다는 보장이 아니라 최소한 그만큼은 잔다는 보장이다. 스케줄러 사정에 따라 100ms 를 재웠는데 실제로는 103ms 가 지나 있을 수 있고, 오차는 항상 길어지는 쪽으로 붙는다. 실험 A 는 9.9초와 10.0초라는 0.1초 간격을 보는 건데 그 오차가 간격에 비해 작지 않다. 그래서 `TimeSource` 인터페이스를 하나 두고, 테스트에서는 시간을 직접 지정하는 구현을 넣었다.

```kotlin
fun interface TimeSource {
    fun nowMillis(): Long
}

class ManualTimeSource(initialMillis: Long = 0L) : TimeSource {
    private var currentMillis: Long = initialMillis
    override fun nowMillis(): Long = currentMillis
    fun advanceToMillis(millis: Long) { currentMillis = millis }
}
```

시계를 9.9초로 보내고 싶으면 그 값을 그대로 넣으면 된다. 아래에 나오는 표들은 전부 이 구조 덕분에 나온 것이고, 몇 번을 돌려도 같은 결과가 나온다.

## 2. 실험 A — 들은 문장 확인하기

9.9초에 5개, 10.0초에 5개를 요청한다. 0.1초 사이에 10개를 몰아넣는 셈이다.

```
time(ms) | requests | fixed-window | token-bucket
    9900 |        5 |            5 |            5
   10000 |        5 |            5 |            0
 합계     |       10 |           10 |            5
```

고정 윈도우는 10개를 전부 통과시켰다. 초당 0.5개로 막겠다고 걸어둔 설정인데 0.1초 구간만 놓고 보면 순간 허용률이 100 req/s 다. 9.9초의 5개는 첫 구간 카운터를 쓰고 10.0초의 5개는 새로 열린 구간 카운터를 쓰기 때문이다. 두 카운터는 서로의 존재를 모른다.

토큰 버킷은 뒤쪽 5개를 전부 거절했다. 9.9초에 토큰을 다 썼고, 0.1초 동안 채워진 토큰은 0.05개뿐이기 때문이다. 애초에 구간 경계라는 개념이 없으니 경계에서 문제가 생길 일도 없다.

여기까지는 들었던 대로였다. 다만 “두 배가 통과한다” 는 말이 실제로는 200배(0.5 req/s 설정에 100 req/s 순간값)로 나타난다는 건 직접 세어보기 전에는 몰랐다. 두 배라는 건 구간 총량을 기준으로 한 이야기고, 시간을 짧게 끊어서 보면 배수가 훨씬 커진다.

## 3. 실험 B — 예상 못 한 쪽

내친김에 반대 상황도 확인해봤다. 5개를 모두 소진한 뒤 2초 간격으로 하나씩 요청하는 경우다.

```
time(ms) | fixed-window | token-bucket | token retry-after(ms)
    2000 |         DENY |        ALLOW |                     0
    4000 |         DENY |        ALLOW |                     0
    6000 |         DENY |        ALLOW |                     0
```

이번에는 고정 윈도우 쪽이 더 빡빡하게 나온다. 평균 허용률은 같은데도 그렇다.

남은 8초 동안은 어떤 요청을 보내도 거절이고, 다음 구간이 열리는 순간 5개가 한꺼번에 풀린다. 토큰 버킷은 2초마다 하나씩 채워지니 요청도 2초에 하나씩 통과한다. 허용하는 총량은 같고, 그것을 시간축에 펴서 내보내는 것뿐이다.

이 부분이 이번에 가장 크게 남았다. **버스트(실험 A)와 starvation(실험 B)은 서로 다른 문제가 아니라 같은 원인에서 나온다.** 리셋되는 시점이 있다는 것 하나가 양쪽을 다 만든다. 여기서 starvation 은 무기한 굶는다는 뜻이라기보다, 다음 리셋 전까지는 무엇을 보내도 통과하지 못하는 구간이 생긴다는 의미다. 외운 지식으로는 A 만 알고 있었고, B 가 그 반대편이라는 건 생각해본 적이 없었다.

## 4. 429 에 뭘 실어 보낼까

구현하다 보니 `allowed` 값만으로는 부족했다. 거절할 거면 언제 다시 요청하면 되는지도 같이 알려주는 편이 낫다.

```kotlin
data class RateLimitDecision(
    val allowed: Boolean,
    val remaining: Int,
    val retryAfterMillis: Long,
)
```

그런데 이 값을 계산하는 방식이 두 리미터에서 꽤 다르게 나온다.

- 고정 윈도우는 다음 구간이 열릴 때까지의 시간이다. 실험 A 의 마지막 거절은 10,000ms 였다. 방금 요청한 사람에게 10초를 통째로 기다리라고 안내하는 셈이다.
- 토큰 버킷은 모자란 토큰이 채워질 때까지의 시간이다. 다 쓴 직후에는 2,000ms 고, 1초 뒤에 다시 물어보면 1,000ms 로 줄어 있다.

클라이언트 입장에서는 두 번째가 훨씬 쓸모 있다. 기다린 만큼 값이 줄어들기 때문에 재시도 타이밍을 잡을 수 있다. 반면 고정 윈도우는 대기 시간이 전부 같은 시각, 그러니까 구간 경계를 가리킨다. 거절당한 클라이언트들이 다 같이 그 순간에 재시도한다는 뜻이고, 결국 리미터가 경계 버스트를 스스로 만들어내는 구조가 된다.

## 5. quota 를 얹으면 사용량 제한 아닌가

여기까지 만들고 나서 든 생각이다. 지금 만든 건 짧은 시간에 요청이 몰리는 걸 막는 쪽이다. 여기에 하루 총량을 하나 더 붙이면 API 사용량 제한의 기초 틀이 되지 않을까 싶었다.

그래서 만들어봤는데, 구현하다 보니 quota 가 결국 윈도우 크기가 하루인 고정 윈도우였다. `now / 86_400_000` 으로 날짜 ID 를 만들고 날이 바뀌면 카운터를 버린다. 실험 A 에서 문제 삼았던 구조 그대로다.

그러면 quota 에도 경계 버스트가 생기는 것 아닌가 하는 생각이 들었다. 23:59 에 1,000개, 00:00 에 또 1,000개.

실제로 생긴다. 그런데 이건 굳이 막을 필요가 없다. 순간적인 버스트는 아래에 깔린 토큰 버킷이 이미 잡고 있고, “하루 1,000회” 라는 약속 자체는 두 날 모두 지켜졌기 때문이다. 자정에 사용량이 초기화되는 것도 쓰는 사람 입장에서는 오히려 기대하는 동작이다.

**같은 리셋이 한 층에서는 결함이 되고 다른 층에서는 사양이 된다.** 층을 나누는 이유를 여기서 봤다.

## 6. 합쳐놓으니 함정이 있었다

두 층을 모두 통과해야 허용하는 합성 리미터를 만들었다. 처음에는 20줄이면 끝날 줄 알았는데 그렇지 않았다.

`tryAcquire` 는 통과 여부만 알려주는 함수가 아니다. 통과하는 순간 카운터를 올려버린다. 그런데 합성 리미터는 이걸 두 번 호출한다.

quota 를 먼저 검사해서 통과했는데 그다음 토큰 버킷이 거절하면 어떻게 될까. 요청은 실패했는데 quota 만 깎인 상태가 된다. 거절당한 요청이 하루치를 먹는 셈이다. 429 를 받은 클라이언트는 보통 재시도를 하고, 그 재시도가 또 토큰이 없어서 막히면 quota 만 다시 깎인다. 극단적으로는 성공한 요청이 하나도 없는 채로 하루치를 다 태울 수도 있다.

그래서 거절을 두 갈래로 나눴다.

```kotlin
val quotaDecision = quota.tryAcquire(subject, permits)
if (!quotaDecision.allowed) return quotaDecision   // quota 가 막음 — 깎인 게 없다

val rateDecision = rate.tryAcquire(subject, permits)
if (!rateDecision.allowed) {
    quota.release(subject, permits)                // 토큰 버킷이 막음 — 깎인 quota 를 되돌린다
    return rateDecision
}
```

quota 가 막았다면 카운터를 올린 적이 없으니 그대로 나가면 된다. 토큰 버킷이 막았을 때만 이미 깎인 quota 를 되돌린다.

검사 순서를 quota 부터로 잡은 이유는, 되돌릴 일이 생기는 쪽이 항상 먼저 검사한 층이기 때문이다. quota 를 먼저 보면 되돌리는 기능을 quota 에만 만들면 되고 토큰 버킷은 한 줄도 고치지 않아도 된다. 순서를 뒤집으면 토큰 버킷에 환불을 붙여야 하는데, 버킷은 시간에 비례해 저절로 차오르는 구조라 충전된 토큰과 되돌린 토큰이 섞이면서 capacity 를 넘길 여지가 생긴다.

## 7. 막는 층이 넘어가는 순간

합쳐놓고 다시 돌려봤다. quota 는 하루 8개, 버킷은 capacity 5 에 초당 0.5개 충전이다.

```
time(ms) | requests | allowed | retry-after(ms)
       0 |        6 |       5 |            2000
    2000 |        1 |       1 |               0
    4000 |        1 |       1 |               0
    6000 |        1 |       1 |               0
    8000 |        1 |       0 |        86392000
```

0초에는 버킷이 막는다. 6개 중 5개만 통과했는데 용량이 5이기 때문이다. quota 는 8까지 여유가 있는데도 여기서 걸린다.

8초에는 quota 가 막는다. 토큰은 방금 하나 채워졌는데 하루치를 다 썼기 때문이다. 대기 시간이 86,392,000ms 로 나오는데, 자정까지 23시간 59분 52초다.

같은 사용자가 같은 API 를 부르는데 8초 사이에 막는 층이 넘어갔다. 대기 시간이 4자리에서 8자리로 뛰는 지점이 그 경계다.

클라이언트 입장에서 이 둘은 성격이 완전히 다른 신호다. 2초는 잠깐 기다렸다 다시 보내라는 뜻이고, 23시간은 오늘은 끝났다는 뜻이다. 그런데 지금 구현은 둘을 같은 모양으로 내려보낸다. 같은 429 에 `Retry-After` 값만 다르게 주는 게 맞는지, 아예 다른 코드로 갈라야 하는지는 아직 판단이 안 선다.

표에 드러나지 않는 것도 하나 있다. 0초의 6번째 요청에서 되돌린 quota 1개다. 그게 없었다면 8초의 거절이 6초로 당겨져서 찍혔을 것이다.


## 8. 알게 된 것과 여전히 모르는 것

들은 문장 하나를 근거로 바꾼 것, 이번에 가장 크게 남은 것이다. 덤으로 외운 문장이 알려주지 않던 반대편(실험 B)이 있다는 것도 알게 됐다.

여전히 모르는 것도 정리해둔다.

- 성능. 세 구현 어디에서도 처리량이나 지연을 재지 않았다. 부하 테스트가 없다.
- 동시성. `compute` 로 층별 원자성은 잡았는데 멀티스레드 테스트는 아직 안 짰다.
- 다중 인스턴스. 전부 단일 프로세스 인메모리다. 서버가 여러 대면 각자 자기 맵을 들고 있으니 실제 허용률은 대수만큼 곱해진다. [Redis 를 앞단 필터로 두고 재봤을 때](/posts/redis-filter-db-reach-remeasured/)처럼 상태를 밖으로 빼면, 원자성을 어디서 잡을지가 통째로 다른 문제가 될 것 같다.
- 429 를 어떻게 설계할지. 7번에 적은 그 질문이다.
