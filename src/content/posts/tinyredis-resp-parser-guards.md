Go로 만들고 있는 미니 Redis(tinyredis), 이번엔 RESP 파서 안쪽 얘기다.

[앞 글](/posts/redis-cli-tinyredis-resp/)에서 RESP가 뭔지, 왜 redis-cli가 내 서버에 붙는지까지 다뤘다.
파서와 직렬화를 합쳐 107줄짜리 코드고, 만드는 데 오래 걸리지도 않았다.
만들고 나서 남은 고민은 파싱이 아니라 그 주변에 있었다.

클라이언트가 말한 길이를 믿어도 되는가.
에러가 났을 때 연결을 끊어야 하는가, 유지해야 하는가.

## 그 길이는 클라이언트의 선언이다

RESP 파싱의 핵심은 `$5` 를 읽고 다음 5바이트를 통째로 읽는 것이다.
스캔도 이스케이프도 없다. 앞 글에서 이걸 길이 접두의 장점으로 적었다.

그런데 이 문장을 서버 입장에서 다시 읽으면 이렇게 된다.
**클라이언트가 선언한 크기만큼 서버가 버퍼를 잡는다.**

```go
size, err := strconv.Atoi(line[1:])
// ...
buf := make([]byte, size+2)
```

악의적인, 혹은 그냥 버그 있는 클라이언트가 `$2147483647` 을 보내면
서버는 2GB 버퍼를 할당하려다 넘어진다. 연결당 goroutine 모델이니
이런 연결이 여러 개면 피해는 연결 수만큼 곱해진다.

구분자 프로토콜에는 없던 종류의 문제다.
파싱이 단순해진 대가로, 메모리 할당의 결정권 일부가 클라이언트 입력으로 넘어간 것이다.
길이 접두를 쓰는 순간 "선언을 검증할 책임"이 세트로 따라온다.

그래서 `Atoi` 직후, `make` 직전에 상한을 검사한다.

```go
const (
	maxArrayLen = 64
	maxBulkLen  = 512 * 1024
)

size, err := strconv.Atoi(line[1:])
if err != nil || size < 0 || size > maxBulkLen {
	return "", fmt.Errorf("%w: invalid bulk string size %q", ErrProtocol, line[1:])
}
```

수치는 워크로드에서 나왔다. tinyredis가 처리하는 명령은 `SET key value EX 10` 이 제일 길다.
인자 64개, 값 512KB를 넘을 정상 요청이 없으니 그 위는 전부 거절해도 잃는 게 없다.
진짜 Redis도 같은 자리에 `proto-max-bulk-len`(기본 512MB)을 두고 있다 —
상한값이 다른 건 서비스가 감당하기로 한 페이로드 크기가 달라서지, 구조는 같다.

배열 길이 쪽은 `n < 1` 도 거절한다. 빈 배열은 명령 이름조차 없는 요청이라
dispatch에 넘겨봐야 할 수 있는 게 없다.

위치도 중요하다. 이 검사를 dispatch 단계에서 하면 늦는다.
dispatch에 도착했다는 건 이미 버퍼를 잡고 본문을 다 읽었다는 뜻이다.
신뢰 경계는 바이트가 값으로 바뀌는 지점, 그러니까 파서다.

## 에러를 세 갈래로 나눈 이유

길이 검증을 넣고 나니 다음 질문이 자연스럽게 따라왔다.
검증에 걸리면, 그다음에 뭘 하나. 에러를 답하고 계속 받나, 끊나.

정리하고 보니 에러는 세 갈래였다. dispatch 앞에 주석으로 박아둔 분류다.

```
클라이언트 잘못  = -ERR 응답 후 연결 유지
프로토콜 위반    = -ERR protocol error 후 연결 종료
I/O 에러        = 조용히 종료
```

`GET` 인자가 모자라거나 모르는 명령이 오는 건 클라이언트 잘못이다.
프레임 자체는 멀쩡하게 읽었으니 에러를 답하고 다음 명령을 계속 받으면 된다.

프로토콜 위반은 다르다. `*3` 이라더니 `$` 가 안 나온다든가, CRLF가 깨져 있다든가,
그리고 위의 길이 상한 초과도 여기다. 이때 연결을 유지하면 안 되는 이유가 있다.
길이 접두 프로토콜에서 프레임 경계를 잃으면,
지금 읽기 위치가 명령의 시작인지 어느 값의 중간인지 알 방법이 없다.
계속 읽으면 남의 데이터 조각을 명령으로 오독하게 된다.
안전한 행동은 연결을 끊고 클라이언트가 새로 시작하게 하는 것뿐이다.

I/O 에러는 상대가 이미 사라진 경우라 에러 응답을 보낼 곳 자체가 없다. 조용히 정리한다.

기준을 한 줄로 접으면 이거다.
**다음 프레임을 신뢰할 수 있는가.**
신뢰할 수 있으면 연결은 산다(클라이언트 잘못). 신뢰할 수 없으면 죽는다(프로토콜 위반).
신뢰를 따질 상대가 없으면 정리만 한다(I/O).

## dispatch의 error는 클라이언트 에러가 아니다

이 3분류를 코드에 옮기면서 시그니처 고민이 하나 있었다.

```go
func (s *Server) dispatch(w *bufio.Writer, args []string) error
```

모르는 명령이 왔을 때 dispatch가 `errors.New("unknown command")` 를 반환하는 설계를
먼저 떠올렸는데, 그러면 호출부가 매번 물어야 한다.
"이 에러는 클라이언트한테 답할 에러인가, 연결을 접을 에러인가."
에러 값 하나에 의미가 두 개 실리고, 분류 책임이 호출부로 샌다.

그래서 뒤집었다. 클라이언트 잘못은 dispatch 안에서 `-ERR` 응답을 쓰는 것으로 끝나는
**정상 흐름**이고, dispatch의 반환값에는 나타나지 않는다.

```go
case "GET":
	if len(args) != 2 {
		return wrongArity(w, "get") // -ERR 를 쓴다. 반환되는 건 "쓰기"의 에러다
	}
```

`wrongArity` 가 반환하는 건 `resp.WriteError` 의 결과, 그러니까 소켓 쓰기의 성공 여부다.
dispatch가 non-nil error를 반환하는 경우는 단 하나, 응답을 쓰다가 실패했을 때뿐이다.
호출부(연결 루프)는 그래서 단순해진다 — `err != nil` 이면 그냥 연결을 접는다.
클라이언트 잘못인지 판별할 일 자체가 없다. 그건 dispatch 안에서 이미 끝난 얘기라서다.

3분류가 함수 경계에 그대로 새겨진 셈이다.
프로토콜 위반은 `ReadCommand` 의 `ErrProtocol` 로, I/O 에러는 dispatch의 반환값으로,
클라이언트 잘못은 에러가 아닌 것으로.



파서를 다 만들고 보니, 진짜 작업량은 "정상 입력을 파싱한다"가 아니라
"비정상 입력에도 서버가 예측 가능하게 행동한다"에 있었다.
길이 가드도, 3분류도, 시그니처 설계도 전부 후자다.
